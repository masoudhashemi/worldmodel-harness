# Methods and prompts for improving the operational world model

The strongest near-term candidates are **compact action interfaces, task-local graph retrieval, evidence-backed rule testing, and trace-grounded artifact proposals**. These connect stored experience to execution. More reflection agents or longer persistent instructions are not, by themselves, improvement mechanisms.

This comparison retains all **17 local papers**, using P01–P17 from [literature and formulation](literature-and-formulation.md#paper-by-paper-mathematical-formulations), plus the six cognitive/neurosymbolic references in the [paper guide](../papers/README.md). The [standardized formulation](formulations.md#part-i-standardized-comparison-framework) remains the mathematical reference. This companion adds methods, prompt contracts, code evidence, and implementation candidates.

Source check: 2026-10-16. PDF pages are one-based. Prompt descriptions below are **paraphrases**, with locators for literal templates. “Not located” means no author implementation or complete template was established from the inspected paper, linked artifacts, and targeted searches—not that none exists. Code checks are static inspection of selected mechanisms, not reproduction of scores. No external implementation was executed or imported into our harness.

Two implementation distinctions matter especially. First, **prompt requirements and enforced invariants are different**: WorldAbduct prescribes controlled tests but accepts a model verification verdict; PG’s tool-name constraint in the refiner prompt is distinct from topology validation (PDF p. 24). Second, **stored artifacts and usable artifacts differ**: Harness2’s prompts require triggers and existing helper files. Our equivalents are discoverable artifact menus and resolvable versioned dependencies. More stored procedures without invocations do not establish improvement.

## 5 Mapping to our implementation

Implementation update: the original candidate table below records the audit-time gaps. The `operational-learning-v2` changes now implement compact action/evidence references, one bounded semantic-output repair, action/subgoal-focused retrieval, task requirement checks, prospective response-rule support/dispute, trace-localized artifact proposals, and per-invocation reuse measurements. See the [current implementation and limits](../README.md#operational-learning-v2-implementation). Mandatory task-check state is losslessly compressed, not truncated. These mechanisms have deterministic tests, not a measured benchmark improvement. Broad causal-rule promotion, learned retrieval, and measured counterfactual savings remain open.

Feedback clarification: grader-assisted learning is a valid configuration of the multi-source architecture. The transfer constraints below describe the current trajectory-only experiment, not a permanent ban on grader feedback. Scalar scores, diagnostic feedback and answer-conditioned demonstrations must be separately declared channels; task feedback does not itself establish an environment rule.

The following are **our engineering hypotheses**, not established improvements. They preserve the goal: learn operational relations from permitted interactions, retrieve useful evidence, and improve execution support—not encode benchmark solutions.

### Mechanisms requiring an explicit protocol or architecture choice

| Mechanism | Reason |
| --- | --- |
| Answer-conditioned references and score-based adoption from P05/P06/P09/P10/P13 | Compatible with a declared feedback-assisted configuration. Specify score, diagnostic or demonstration access separately; repeated tasks alone do not authorize all three. |
| Evo2 evolver training, TreeFlex RL, Harness-G SNC | Requires weight training/rewards/compute. A frozen-model approximation is a different method. |
| Hyperagents-style modification of the whole controller | Conflicts with fixed interpreter, tool permissions and evaluation boundary. |
| Full tree restoration for business actions | Restoring context does not undo messages, records or unknown writes; isolation/restoration must exist first. |
| Benchmark-specific endpoint/tenant recipes | Replaces learning with engineering answers. Transfer mechanisms; learn relations and applicability. |
| Larger always-on reflection/checklist prompts | Additional context can cost more than it helps; test targeted/on-demand guidance instead. |
| Promotion on an LLM’s plausible/verified verdict alone | Citation provenance and model agreement are not empirical verification. |

## 6 Candidate prompt contracts for our code

These are **our contract sketches**, not paper quotations. The implementation update above identifies the installed portions and their limits; the table is not a claim that every proposed capability is complete. Runtime checks must enforce the installed interfaces.

| Role | Inputs | Concise proposed contract | Controller enforcement |
| --- | --- | --- | --- |
| Next action | Subgoal, working graph, bindings, tools/budget | Select one action, cite supplied IDs. Query missing prerequisites. Predict only observable fields. Leave optional explanations empty unless they distinguish a current failure. | Resolve IDs, scope/check prerequisites, dispatch once, record observation. |
| Consolidation | Relevant episodes, existing scoped rules, evidence menu | Return a small batch of new/revised/duplicate-candidate rules or no change. Specify conditions, prediction, competing explanation, citations and falsifying observation. | Validate references/types; uncertain duplicates remain separate; hypotheses do not become facts by declaration. |
| Investigation | One hypothesis, alternatives, permitted tools/budget | Choose the cheapest distinguishing observation and expected outcomes; return unresolved if no permitted observation distinguishes them. | Permissions, route/budget, actual observations, coverage and stopping rule. |
| Artifact proposal | Recurring mechanism, trace slices, prior attempts, costs | Propose bounded artifact or no change: trigger, bindings, required claims, failure/stop behavior and predicted runtime effect. Label unknown benefit; do not require already-measured savings for an unbuilt candidate. | Validate interpreter data/dependencies; bounded experiment before stronger deployment status. |
| Completion check | User requirements and current evidence | Map every required output/change to observation or gap. API success alone is not completion. | No hidden grader access; bounded permitted checks; preserve requested output shape. |

These contracts do not prescribe table joins, tool bindings or business rules. Those remain learned, scoped objects. Generic controller logic determines how evidence and artifacts may be used.

## 7 Evaluation sequence

The previous three-round run was stopped at the user's request. Preserve it unchanged; use a fresh run for the implementation update. Changing prompts, models or learners between rounds would undermine the within-run comparison.

1. Attribute output-limit, schema/citation, gate, discovery, verification and reasoning failures from actual boundaries—not exception names alone.
2. Test compact interfaces with the same model/tasks, fixed budgets, a fresh store and matched unchanged arm. Reliability gains alone do not establish learned-knowledge value.
3. Isolate retrieval and goal-evidence changes using a fixed learned snapshot. All 50 tasks remain in the score denominator; no new held-out set is needed for this in-sample objective.
4. Test rule verification, then artifact reuse, against identical online learning without each added mechanism. Require evidence → scoped rule → retrieval/artifact → actual invocation → outcome/cost change.
5. Repeat the same 50 tasks for three fixed-control rounds; report paired gains/regressions and total cost. A no-update repeated-run arm separates learning from some runtime/model variation and is not a validation split.

The current runtime keeps grader output reporting-only. The architecture also supports explicit score/diagnostic-assisted hypothesis generation, proposal and selection through the evaluation graph; answer-conditioned demonstrations are a distinct channel. Success is better verified task execution after learning costs, not increased memory size.
