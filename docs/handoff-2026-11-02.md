## 1. Goal and how results are judged

- **Goal:** an operational world model (a graph learned from experience) that makes Gemma-4-31B on the Stirrup harness better at AutomationBench tasks.
- **The user's criterion:** accuracy and time together.
  - Fewer turns at higher latency is a failure.
  - Lower cost alone (calls, tokens) is not a win.
  - Report strict, partial, median time and mean time, always paired by task against a same-day control arm.
- **Grades are never used for learning,** only for offline diagnosis and for validating variants.
- **The user's core idea (v3):**
  - the graph organises experience so that, at a node with a given query, it knows the likely successful local plans;
  - queries that differ only on the surface (names, ids, emails) reuse that knowledge;
  - the graph keeps learning over time and never freezes.
- **Agreed design (2026-11-01):** the transition graph holds no task values.
  - Edges hold the next action and, for each argument, where its value comes from.
  - A per-run state (the query plus the responses so far) supplies the values.
- **Working rules:**
  - Commit or push only when the user asks; nothing has been committed since `6ff061e`.
  - The user wants honest, noise-aware reporting.

## 3. What the evidence says, in short (E014–E022)

- **Text that steers Gemma up front hurts or does nothing.** This covers route notes, advisory text, checklists, ledger reviews and dead-end wording (E014–E017, E019–E020).
- **Code-made, reactive, concrete corrections help.**
  - E018's fix memory cut calls by 17–26% and time by about 20% where it fired, and the result replicated in E019.
  - The note must name the exact missing argument with an example, e.g. `body='{...}'`.
- **E021's `max_tokens` 4096 plus one retry** removed the reproducible 1200 s runaway (a search query repeated for more than 80k characters).
- **Noise:** two identically configured arms on the same day differ by about 5 of 45 tasks strict. Credit accuracy changes only across replicates (variants or rounds).
- **Where failures come from (v2 analysis):**
  - 66% of baseline failures are near misses on write content or coverage;
  - about 14% are malformed-write loops;
  - none are "could not find the endpoint".

  Endpoint discovery therefore costs time, not accuracy.
- **Offline (v3 §8–9.5):**
  - next-endpoint prediction transfers to renamed variants (top-1 0.66–0.72);
  - argument fill-in learns across variants (calls fully right 0.05 → 0.11 → 0.17), but its precision (0.67–0.76) is too low to apply automatically;
  - stale literals from other runs account for 0% of fill-in; an earlier 46% figure was inflated by Gemma repeating its own choices.

## 4. The v3 design as built

- **Transition graph** (`experience.Model`, persistent across runs, holds no task values):
  - **Plans:** counts of the next successful fetch, keyed by (query template, last two successful fetches), with the last fetch alone as a fallback. Counted at most once per episode.
  - **Gate:** a plan step is shown when its Wilson lower bound (Z = 1.2816) is ≥ 0.35. One consistent earlier run is enough. Up to 3 distinct steps.
  - **Argument rules** per slot, counted at three levels: (template, action, slot, nth) → (template, action, slot) → (any, action, slot). A rule is one of:
    - `Query(type,k)`;
    - `Resp(field[|anchor]) <- action`, where the anchor is `key=Query(..)`, `key@query` (the record whose name the query mentions) or `?` (the agent chooses the record);
    - `Agent`;
    - `Const`, only for API-shape literals: the same value in ≥2 workflows and ≥80% of the workflows that use the slot.
  - **Learning:** `Model.add(episode)` after each trial, from tool calls and results only. Each argument value is traced to a rule by `lifting.source`, and the value itself is dropped.
- **State** (per run, held in `ExperienceAdvisor`): the query text, its template and bindings, and every `api_fetch` with its response. Only successful calls count.
- **`Model.resolve`:** for each level, if `Agent` is the top rule, the argument is left to the agent, unless it is a shape constant. Otherwise rules are tried in order of support through `lifting.fill` against the state. If nothing resolves, the best rule comes back with no value, and the plan shows a placeholder such as `<id from call 1>`.
- **Delivery:** after each `api_search`, an `[Experience]` note lists the plan steps as calls, with hits/total. Values come from this run's state where they resolve. An identical plan is not repeated.
- **Known looseness:** `fill` with a `key@query` anchor takes the first record the query mentions, without checking that it is the only one. `source` does require uniqueness when it learns the rule. It is a one-line fix in `lifting.fill`.

## 5. E022 result: the learning stream (finished 2026-11-02)

Run: `runs/e022-learning-stream`, 405 trials. Arms:
- **baseline;**
- **fixes:** E018 memory, frozen;
- **learning:** fixes plus live plans, with the graph updated after each of its trials. It starts from all runs outside these 45 workflows.

Learning minus fixes, paired by task:

| Round | Plans shown | Strict | Partial | Median time | API calls/task | Input tokens |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| v1 (no plans possible) | 0/45 | −2 | −0.04 | 0 s | −0.2 | −3% |
| v2 | 32/45 | +2 | +0.04 | 0 s | −4.7 | −27% |
| v3 | 30/45 | 0 | +0.03 | 0 s | −4.2 | −17% |

**Verdict:** cheaper runs (about 12% fewer API calls, 17–27% fewer input tokens), but no faster and no more accurate. The gap did not grow from v2 to v3. By the user's criterion this is not a win.

**Why (adherence analysis, `scripts/e022_plan_adherence.py`):**
- **Time follows turns.** Wall time equals model time (4–5 s per turn), and Gemma batches about 1.8 tool calls per turn. Plans removed mostly parallel searches. Tool calls fell 13% but turns only 10%, and the paired median saving is 0.5–1 turn.
- **Step 1 is taken 33% of the time.** Resolved steps were followed 51% of the time, steps with placeholders 23%. The most common reaction (41%) is another search.
- **The extra searches are mostly discovery for the write and notify parts of the task**, which the plan doesn't cover. Plans predict the next 1–3 reads, which Gemma would make anyway.
- **Auto-executing resolved GET steps** would save at most about 23 turns over 90 trials, about 1 s per task. Not worth it.

## 6. Next steps, in order

### 6.1 Offline bound for collapsing discovery (do first, no live runs)

**Why:** this is the only remaining lever for time that the graph can reach.
- In fixes trials (v2 and v3), about 7 of 24 turns per task are search-only.
- The graph already knows each workflow's full endpoint set from earlier runs, including the write and notify endpoints.
- If the documentation for those endpoints came back with Gemma's *first* search, the later sequential search turns could go away.
- This is search-result content (API docs Gemma requests and uses), not advisory text, so it stays inside the "code-delivered, concrete" class that has worked.

**Method:** in the E022 learning trials (v2 and v3), using the graph as it stood before each trial (rebuild with `experience_graph` in replay order):
1. Take the set of endpoints the graph knows for this template: actions with support in `Model.arguments[(template, action)]`, or in `fetches` keys for the template.
2. For each search-only turn after the first search, check whether every endpoint Gemma fetched next, up to its next search turn, was already in that set. If so, the turn was avoidable.
3. Report avoidable search turns per task, and their share of all turns. Their time is about 4–5 s each.
4. Also report, per workflow, how many API docs would have to be returned, as a context-cost check.

**Go/no-go:** if the bound is under about 2 turns per task (about 10 s against a 60 s median), stop the plan line and report that the v3 graph's value is cost, not time.

### 6.2 If 6.1 says go: implement discovery prefill (E023)

**Mechanism:** on the first `api_search` of a run whose template has a history:
- append, as additional search results in the same JSON schema `api_search` returns (`id`, `method`, `description`, `parameters`, `response`, `url`), the entries for the workflow's known endpoints;
- order them by plan order;
- record them in the result log.

**Data:** the graph needs a doc store keyed by endpoint (action) → the search-result entry. Build it from `api_search` tool results in trajectories: the entry whose `method` + `url` normalises (`fixes.endpoint`) to the action. Use docs only, never values.

**Keep:** the fix memory, the cap, the repeat-only unavailable note. Decide whether to keep or drop the `[Experience]` plan text with an A/B. Plain docs may do better than plan text.

**Experiment design:**
- Same variant stream (v1 → v3, 45 workflows), arms fixes vs learning-prefill.
- Optionally drop the baseline to save about 4 h; E022 already has same-setup baselines, though same-day controls are the rule. Ask the user.
- Primary measures: paired median turns and median time in v2 and v3, with v1 as the A/A noise reference.
- Secondary: strict and partial, which must not drop beyond noise.
- Tests: unit-test the doc store and the prefill, in the style of `tests/test_experience.py`.

### 6.4 The accuracy side (not addressed by v3 so far)

- **Failure profile:** most failures are near misses in write content or coverage (66%). The transition graph does not touch that.
- **What can help, from the evidence:** only code-made, concrete comparisons. Showing state does not; E017 showed Gemma doesn't compare shown state against the task rules.
- **A candidate from v3's delivery list** (`world-model-v3.md` §4.5) is a pre-send check:
  - when a write call's arguments disagree with what the graph's argument rules resolve from the state (for example the wrong record id, where `fill` gives a confident value), name the specific mismatch;
  - use rules with high support only.

  Measure first, offline: how often successful write calls in failed trials disagree with a confident resolved value, and how often those disagreements match a failed grader check (diagnosis only).

### 6.5 Things not to retry

- Route notes, "find another source" or dead-end notes, checklists, ledger and finish reviews. All were tested in E015–E020 with no gain or with harm.
- Applying argument fill-in automatically. Offline precision of 0.67–0.76 is too low.
- Auto-executing planned GETs (ceiling of about 1 s per task, section 5).
